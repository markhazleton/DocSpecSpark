# Appendix C: Troubleshooting Guide

## Installation and Setup

### Slash commands are not appearing in my agent's autocomplete

**Symptoms:** After running the quickstart prompt, the `/devspark.` commands do not appear in your agent's command list.

**Diagnosis steps:**

1. Verify the agent shim files were created:
   - Claude Code: `ls .claude/commands/ | grep devspark`
   - GitHub Copilot: `ls .github/prompts/ | grep devspark`
   - Cursor: `ls .cursor/prompts/ | grep devspark`

2. Verify the framework defaults are installed:
   - `ls .devspark/defaults/commands/ | wc -l` — should show 28 files

3. Verify the VERSION file is present:
   - `cat .devspark/VERSION` — should show a version string like `2.1.0`

**Fixes:**

- **Restart your IDE completely.** This is the most common fix. IDE extensions load command files on startup, not on file creation. A reload window is not enough — restart the application.
- **Re-run the quickstart prompt.** It is idempotent — running it again will refresh any missing files without touching your constitution.
- **Check your agent's documentation.** Some agents require additional configuration to enable slash commands or local command files.

---

### The quickstart prompt returns an error or times out

**Symptoms:** Pasting the quickstart URL produces an error like "Could not fetch" or "Connection refused."

**Diagnosis:** The quickstart prompt requires internet access to fetch the installation file from GitHub.

**Fixes:**

- Verify internet connectivity from your development machine
- Check that your corporate network/firewall allows access to `raw.githubusercontent.com`
- If internet access is blocked, use the [manual installation](installation.md) approach: clone the DevSpark repository and copy files manually

---

### DevSpark was installed but the constitution is empty or missing

**Symptoms:** `.documentation/memory/constitution.md` is missing or contains only placeholder text.

**Fix:** Create a constitution manually:

```text
/devspark.constitution [Your project's principles here]
```

Or for existing projects:

```text
/devspark.discover-constitution
```

## Commands and Workflow

### The AI is not following my constitution

**Symptoms:** Code generated by the AI assistant doesn't follow the principles in your constitution. PR reviews don't reference the constitution.

**Diagnosis and fixes:**

1. **Verify the constitution exists:**
   ```bash
   cat .documentation/memory/constitution.md
   ```
   If empty or missing, create one with `/devspark.constitution`.

2. **Make principles specific and measurable.** "Write clean code" is not enforceable. "Functions MUST NOT exceed 50 lines" is. If your principles are vague, the AI has nothing concrete to enforce.

3. **Check that the command is reading the constitution.** In Claude Code, you can verify by asking the AI: "What does the project constitution say about security?" If it can't answer, the file isn't being read.

4. **For large codebases:** Try scoping the operation more narrowly. Instead of site-auditing the entire codebase, audit `src/api/` first.

---

### `/devspark.specify` keeps recommending quickfix for a complex feature

**Symptoms:** You describe a feature that clearly needs a full spec, but the intake classifier recommends quickfix or quick-spec.

**Fix:** You can override the route classification:

```text
/devspark.specify --full Build a payment integration with Stripe including 
webhook handling, refund processing, and reconciliation. This is a major feature.
```

The `--full` flag explicitly requests the full spec route, bypassing classification.

Alternatively, provide more context in the description. If the AI is classifying as quickfix, it may not have enough information to recognize the complexity. Describe the scope explicitly:

```text
/devspark.specify Build a payment integration. This touches: a new payments service,
webhook handler, database schema (3 new tables), reconciliation job, and admin UI.
```

---

### Spec status is stuck at "In Progress" after all tasks are done

**Symptoms:** All tasks in `tasks.md` are marked `[x]`, but the spec status is still `In Progress`.

**Fix:** Update the status manually:

```text
/devspark.implement --status-check
```

If the implement command doesn't automatically update the status, you can update `spec.md` directly — change `**Status**: In Progress` to `**Status**: Complete`. The status field is a text field; the AI commands read it, but there is no enforcement mechanism that prevents manual editing.

---

### `/devspark.pr-review` is generating irrelevant findings

**Symptoms:** PR review produces findings that don't seem related to the actual changes.

**Diagnosis:**

1. The AI may be reviewing files that weren't part of the PR. Specify which files are in scope:
   ```text
   /devspark.pr-review Focus on changes in src/api/users/ and tests/api/users/
   ```

2. The constitution may have principles that are too broad, generating findings for every file that technically violates a principle even if the PR doesn't touch it.

3. The spec status may not be complete, causing the review to include general codebase concerns alongside PR-specific ones.

---

### The critic is flagging everything as a SHOWSTOPPER

**Symptoms:** `/devspark.critic` output has 10+ SHOWSTOPPER findings, and many of them seem theoretical or unlikely.

**Context:** The critic intentionally over-flags. Its job is to surface risks, not block work. SHOWSTOPPERS in critic output are not equivalent to CRITICAL findings in PR review.

**What to do:**

- Review all SHOWSTOPPERS critically. Some will be genuinely important.
- For each one, ask: "If this scenario occurred in production, what would the impact be?"
- For theoretical risks with low probability, document the risk acceptance in the spec: "The critic flagged [X]. This risk is accepted because [reason]. Mitigation: [mitigation]."
- The presence of critic findings does not block implementation. The presence of CRITICAL findings in PR review does.

## Harness Runtime

### `devspark doctor` shows adapter as unavailable

**Symptoms:** `devspark adapter list` shows your preferred adapter as "not available."

**For `claude_code`:** The adapter requires the Claude Code CLI to be installed and on the PATH.
```bash
which claude   # should return a path
claude --version   # should return a version
```

**For `copilot`:** Requires `gh` CLI with the Copilot extension:
```bash
gh extension list   # check if 'gh copilot' is listed
gh extension install github/gh-copilot
```

**Workaround while the preferred adapter is unavailable:** Use `noop` for dry runs and `manual` for steps requiring human input.

---

### `devspark harness run` exits with `EXIT_AUTONOMY_REQUIRED` (exit code 20)

**Symptoms:** Running a workflow with `--non-interactive` fails with exit code 20.

**Fix:** Specify the autonomy level. One of:

```bash
# Via flag
devspark harness run --non-interactive --autonomy autonomous spec.yaml

# Via environment variable
DEVSPARK_AUTONOMY=autonomous devspark harness run --non-interactive spec.yaml

# Via project file
echo "level: autonomous" > .devspark/autonomy.yaml
devspark harness run --non-interactive spec.yaml
```

---

### `devspark resume` fails with `EXIT_RESUME_FAILED` (exit code 25)

**Symptoms:** Attempting to resume a paused workflow fails.

**Cause:** The workflow definition changed between the time the workflow paused and the resume attempt. The `context_checksum` validation detects this change.

**Fix options:**

1. **Restore the workflow to its previous state.** If the workflow was changed in a branch, switch back to the state it was in when it paused.

2. **Start a new run.** If you can't restore the previous state, start fresh:
   ```bash
   devspark harness run spec.yaml
   ```

3. **If the change was intentional:** Start a new run from the beginning. The paused state file is not compatible with the new workflow definition.

---

### Harness run writes unexpected files

**Symptoms:** A harness run modified files you didn't expect it to touch.

**Diagnosis:** Check the telemetry trace:
```bash
devspark harness trace latest
```

**Prevention:** Add `restricted_paths` guardrails to the workflow:

```yaml
guardrails:
  restricted_paths:
    - ".devspark/**"
    - ".documentation/memory/**"
    - "src/auth/**"
    - "*.env"
    - ".github/**"
```

For new or untested workflows, run with `--dry-run` first to see what would be touched.

## Upgrades

### After upgrading, an existing slash command stopped working

**Symptoms:** A command that worked before the upgrade now errors or produces unexpected output.

**Diagnosis:**

1. Check if the stock prompt changed significantly:
   ```bash
   git diff HEAD~1 .devspark/defaults/commands/devspark.{command}.md
   ```

2. Check if you have a team override that conflicts with the new stock prompt:
   ```bash
   cat .documentation/commands/devspark.{command}.md
   ```

**Fix:** If the team override was based on an old version of the stock prompt and the upgrade changed the stock significantly, the override may need to be updated. Compare the override with the new stock prompt and reconcile the differences.

---

### The upgrade command says "Warning: team override may be hiding structural changes"

**Symptoms:** The upgrade warning flag about team overrides.

**This warning is important.** It means:
- The stock prompt file changed in the upgrade
- You have a team override in `.documentation/commands/` for this command
- The team override takes priority over the stock file (by design)
- The update to the stock file is effectively invisible to your team

**What to do:**

1. Read the diff for the changed stock prompt
2. Read your team override
3. Decide whether the stock change should be incorporated into your override
4. If yes, manually update the team override to include the relevant changes from the stock update

## Performance

### Site audit is taking too long

**Symptoms:** `/devspark.site-audit` runs for more than 10 minutes and doesn't complete.

**Fixes:**

1. **Scope the audit:**
   ```text
   /devspark.site-audit Scope to src/api/ only
   ```

2. **Run focused audits by principle:**
   ```text
   /devspark.site-audit Focus on security compliance only
   ```

3. **For very large codebases:** Run the harness runtime version with scoping to specific directories.

---

### Harness runs are slow on large repositories

**Cause:** Guardrail enforcement captures a per-step file baseline. On repositories with thousands of tracked files, this adds latency at each step.

**Fixes:**

1. If no guardrails are needed, remove the `guardrails:` block from the workflow YAML. The enforcer short-circuits and incurs zero cost.

2. Narrow `restricted_paths` to specific directories instead of using broad globs.

3. Use git worktrees for parallel runs instead of running multiple processes against the same working tree.
